## Model Usage Retrieval And Reranking

### 1. 모델 읽기

모델을 쓸 때는 가중치만 보는 게 아니라 설정 파일도 함께 읽어야 한다.

메모에서 짚은 대표 항목은 두 가지다.

- **max_position_embeddings**
  - 입력과 출력 토큰을 합쳐 얼마까지 다룰 수 있는지와 연결된다

- **vocab_size**
  - 모델이 다루는 토큰 종류 수
  - 실제 매핑은 `tokenizer.json` 같은 파일에서 확인한다

### 2. tokenizer와 chat template

모델 사용에서 tokenizer는 별도 모듈로 이해해야 한다.

- **tokenizer**
  - 텍스트를 토큰으로 바꾼다
  - 보통 관련 json 파일을 먼저 내려받는다

- **chat template**
  - `system / user / assistant` 형식으로 입력을 구성한다
  - instruct 모델은 이런 대화 형식으로 추가 학습된 경우가 많다

즉:

- 모델만 보는 것이 아니라
- tokenizer와 입력 포맷까지 함께 봐야 실제 동작을 이해할 수 있다

### 3. 검색기의 두 축

검색기는 크게 두 가지로 나뉜다.

- **키워드 기반 검색**
  - 단어 겹침 중심
  - 대표 예: `BM25`

- **임베딩 기반 검색**
  - 의미 유사도 중심
  - 벡터 공간에서 가까운 문서를 찾는다

메모의 감각으로는 임베딩 기반 검색이 더 간단하고 가성비가 좋다고 정리되어 있다.

### 4. Bi-Encoder 감각

임베딩 검색은 보통 Bi-Encoder 구조를 많이 쓴다.

- 질의와 문서를 각각 임베딩한다
- 두 벡터의 유사도로 관련성을 계산한다

장점은 빠르다는 점이고, 단점은 두 텍스트를 동시에 깊게 비교하지는 못한다는 점이다.

### 5. 검색 성능 높이기

메모에서 제시한 개선 방향은 다섯 가지다.

1. 전처리를 더 잘한다.
2. 더 좋은 임베딩 모델을 쓴다.
3. BM25와 임베딩 검색을 하이브리드로 섞는다.
4. 임베딩 모델을 파인튜닝한다.
5. 검색 실패 시 검색어를 고쳐 다시 찾는 로직을 넣는다.

즉, 검색 품질은 모델 하나만 바꾼다고 해결되지 않고 파이프라인 전체 설계와 연결된다.

### 6. 리랭킹

리랭킹은 1차 검색 결과를 다시 순위 매기는 단계다.

- 초기 검색 점수를 그대로 따르지 않는다
- 마지막에 더 정밀한 판단으로 순서를 다시 세운다

대표 관점:

- **Cross-Encoder**
  - 입력 두 개를 함께 보고 판단한다
  - 분류기처럼 관련성을 직접 계산한다

장점:

- 더 정밀한 판단이 가능하다

단점:

- 비용이 더 비싸질 수 있다

### 한 줄 정리

- 검색은 BM25와 임베딩 검색으로 후보를 모으고, 필요하면 리랭킹으로 마지막 정밀도를 끌어올리는 구조로 이해하면 좋다.
